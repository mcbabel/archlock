# Design notes

Why archlock works the way it does. The user-facing details are in [FORMAT.md](FORMAT.md),
[COMMANDS.md](COMMANDS.md) and [AGENTS.md](AGENTS.md).

## Principles

- **Deterministic and offline core.** `init`, `check`, `accept`, `diff`, `stats` and `graph` use no model and no network; the same input gives byte-identical output (LF, POSIX paths, stable sorting) on every OS. A CI check that varies is worthless. Only `push` and `init --with-summaries` start an agent, and it is always the one the user already has.
- **No native builds.** The TypeScript compiler API extracts TS/JS and the scripts of Vue, Svelte and Astro components; tree-sitter compiled to WASM parses Python and the sketches themselves. `npx archlock` needs no compiler toolchain.
- **No telemetry, no service.** The GitHub Action only uses the workflow's `GITHUB_TOKEN`.
- **archlock checks itself.** The sketches in [`archlock/`](../archlock) describe archlock's own 13 modules, and CI runs `archlock check` on them. Doing so early forced an acyclic internal layering: `core` (model, canonical types, rules, merge) ← `fs`, `config` ← `sketch`, `extract` ← `engine` ← `report`, `init` ← `cli`.

## Runtime and tooling

- **TypeScript 6** as a runtime dependency: TypeScript 7 (the native port) has no stable JS API yet, and the extractor needs `createSourceFile` and `resolveModuleName`.
- **Node 20 or newer.** Dev tools are pinned to Node-20-compatible majors (`commander@14`, `vitest@4`, `tsup@8`).
- **Small dependency set:** `commander` (CLI), `picomatch` (globs), `ignore` (`.gitignore` semantics), `@clack/prompts` (interactive `init`), `web-tree-sitter` with the WASM files of the Python, Go, Rust, Java and C# grammars copied in at build time (`tree-sitter-python`, `tree-sitter-go`, `tree-sitter-rust`, `tree-sitter-java` and `tree-sitter-c-sharp` are dev dependencies; users install no grammar package and compile nothing). The C# grammar is the largest (5.4 MB unpacked, 0.3 MB in the npm tarball); grammars are only loaded when a project has files of their language. In total an install brings 12 packages.
- **The MCP server speaks the protocol itself.** `archlock mcp` needs four tools over stdio: JSON-RPC 2.0 messages, one per line, with `initialize`, `ping`, `tools/list` and `tools/call`. That is about 150 lines; the official SDK brought its HTTP transports and about 90 more packages (including `zod`) into every install. The SDK stays a dev dependency: the tests talk to the server through its client, so compatibility with real MCP clients is still checked.
- **Exit codes:** 0 success, 1 violations, 2 usage, configuration or internal errors, so CI can tell architecture drift from "archlock could not run". Every `--json` payload carries `schemaVersion` and `command`.

## The sketch format

- **Python syntax as notation** for every language: highlighting everywhere, and both people and LLMs read it well. Types are never translated, only canonicalized by a token-level pretty printer (`<…>` → `[…]`, quote style, spacing), so the same type compares equal whether it comes from code or from a hand-edited sketch. A type is written bare only when it is unambiguously valid Python; otherwise it is quoted.
- **Stable layout** in the style of `.pyi` stubs: fixed group order, alphabetical members (enum members and overloads keep source order), long signatures and type-parameter lists wrapped one per line. Moving code around never churns a sketch.
- **Comments are soft content.** They attach to elements by fixed rules ([FORMAT.md](FORMAT.md)), survive `accept`, and never fail CI. Comments of symbols that disappeared are reported, never dropped silently.
- **Renames keep their comments when they are unambiguous.** `accept` pairs a removed and an added symbol (or class member) when their sketch text without name and comments is identical and that shape occurs once on each side; it repeats this with the renames found so far applied, so renaming a class and the function that returns it both match. Anything ambiguous stays a removal plus an addition, and its comments are reported as lost: a wrong guess would attach a person's notes to the wrong code.
- **Receivers and signature decorators.** Where a language has several receiver kinds, the usual one stays `self` and the others are written `self: T` (`self: '&mut Self'`, a Go value receiver `self: Role`), so existing sketches are unchanged and the difference is visible. Modifiers that change how a function can be called (`throws`, `unsafe`, `const`, `extern "C"`) and build variants (`@build`, `@cfg`) are decorators on the `def`, compared as part of its signature. The parser accepts exactly these names, so a typo is an error, not a silent no-op.
- **Enum values are literals, open by default.** `Paid = 2` makes the value part of the contract; `Paid = ...` leaves it open and matches any value, which keeps hand-written sketches short and old sketches valid. Data-carrying members use an annotation (`Circle: '{ radius: f64 }'`), so a value and a payload never look alike.
- **Constructor order is a contract for dataclasses and records.** Their fields are constructor parameters, so their order is part of every positional call. The code side records how many leading fields are constructor parameters; only their order is compared, and the other fields stay alphabetical.
- **Very long types** can be abbreviated to `'<start … (N chars, #8 hex of SHA-256)>'` (`maxTypeLength`, opt-in). The same pure function runs on the code model and on parsed sketches, so `check` keeps comparing plain strings and still detects every change. It is off by default because it hides detail from reviewers and agents.

## Extraction and `check`

- **Ownership:** a file belongs to the module whose matching `__paths__` glob is most specific; ties go to the alphabetically first module.
- **Public API:** with an entry, exactly what the entry exports (following re-exports); without one, everything exported by the module's files. In Python, `__all__` wins; otherwise public names, plus names an `__init__.py` imports from its own submodules. An entry that exports nothing (an empty `__init__.py`) does not define the API.
- **Deep imports:** importing a file of another module directly is reported only when it reaches something private. A file the entry re-exports as a whole (`export * as util from "./util"`, or a file whose every export is public) is public.
- **Resolution** uses the nearest `tsconfig.json` (paths, `extends`, references) and workspace package names, so monorepos work without `node_modules`. Python imports resolve against package roots (repository root, `src/`, directories with `pyproject.toml`/`setup.py`); the standard library is never a dependency.
- **Name collisions without an entry:** when several files of an entry-less module define the same name, each one is qualified with its file path in the module (`ui_button_button__Button`). Keeping only the first would hide the others from `check`, and a new file with a taken name would not show up as a change. The prefix depends only on the file's own path, so it stays stable when further files with that name appear.
- **Components are read through the TypeScript extractor.** Everything outside the script blocks of a `.vue`, `.svelte` or `.astro` file is replaced by spaces (line breaks kept), and the result goes through the normal TypeScript extraction. Imports, line and column numbers and type canonicalization are therefore exactly those of TypeScript, without a template parser. Imports come from every script block; other exports only from blocks that can export (Vue's plain `<script>`, Svelte's module script, Astro's frontmatter). Commented-out scripts, scripts inside Vue's `<template>` or Svelte's `<svelte:head>`, and Astro's `is:inline` and data scripts are skipped.
- **A component is a class, its props and events are fields.** Props and the handler props of events (`onChange`, Vue's `onUpdate:modelValue`) are what a parent can pass, so they form one signature, like a React component's props. Events use Vue's own listener names (`calendar-change` → `onCalendarChange`), so a sketch field matches what a parent writes. Local interfaces and type aliases are expanded into fields so that a changed prop shows up as a changed field; a props type defined elsewhere is a base, because following imports would need a type checker. That file's own sketch catches changes to the type.
- **Route files are not components.** Nothing imports a SvelteKit `+page.svelte` or an Astro or Nuxt page, so a component symbol would only add noise; their other exports (`load`, `prerender`) stay.
- **Framework aliases** resolve when no tsconfig `paths` entry maps them: Vite's `resolve.alias`, SvelteKit's `$lib` to `src/lib` next to `svelte.config.*`, Nuxt's `~` and `@` to its `srcDir`, `app/` (if it exists) or the directory of `nuxt.config.*`, and `~~` and `@@` to that directory. The generated `.svelte-kit/tsconfig.json` and `.nuxt/tsconfig.json` that define them are git-ignored, so a fresh clone resolves the same edges as a built one. The framework configs are code, so archlock never runs them; it reads the common literal forms as text (`srcDir: 'src/'`, `alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) }`, `find`/`replacement` lists, `path.resolve(__dirname, 'src')`). A computed alias is not seen.
- **Template components are dependencies.** A Vue template can use a component that no script imports: Nuxt and `unplugin-vue-components` import it at build time. The `components.d.ts` files these tools generate (and commit) name every such component and its file; for Nuxt projects without one, Nuxt's naming rule (`components/base/Button.vue` → `BaseButton`) gives the same answer. A tag that a script imports, or that has no file in the repository (`<NuxtLink>`), adds nothing.
- **Go packages are modules.** A Go package is a directory and Go's unit of architecture, so `init` makes one module per package directory, with `dir/*.go` as its path (not `dir/**`): a new sub-package is reported as unassigned instead of silently joining its parent. Names follow the import path (`internal/store` → `internal.store`); the root package takes the last element of the module path (`github.com/gin-gonic/gin` → `gin`). In a mixed repository, the rest of the code is detected as before.
- **Go imports resolve through `go.mod`.** Every `go.mod` in the repository (also nested modules and local `replace` targets) maps its module path to a directory; an import resolves to a file of that package directory, so ownership works as for any file. A first path element without a dot is the standard library (`net/http`), `C` is cgo, and anything else is an external module named by the longest matching `require`. No network and no module cache are used.
- **Go methods are attached per package.** Go allows a method in any file of the package, so the extractor collects methods by receiver type and attaches them after all files are read, on copies of the cached facts.
- **Build variants are one name with variants.** Files of one package that define the same name are alternatives for different builds (`_linux.go`, `_windows.go`, `//go:build` lines). Qualifying them like in other languages would turn one function into several. Variants with equal signatures are one symbol; variants that differ are `@overload`s of it, each decorated with its constraint (`@build("windows")`), so every variant is compared. Rust `#[cfg]` variants follow the same rule with `@cfg(…)`. Files with `//go:build ignore` are not part of the package at all (they are usually generators with their own imports).
- **Go types are canonicalized by the same function as TypeScript types.** The pretty printer gained rules for token sequences that only occur in Go (`]` directly before a word, prefix `*` and `~`, `<-` next to `chan`, `)` before `(`, `struct{`/`interface{`), so the gofmt spelling is the canonical form and the sketch parser needs no language switch. The real-world TypeScript sketches were byte-identical before and after this change.
- **Untyped Go constants say so.** `const Version = "1.0"` has no type but a kind; `untyped string` is Go's own term and more useful than `'<inferred>'`. For variables the default type applies (`var Ratio = 0.5` → `float64`), and the few values whose type is evident from the syntax alone (`&T{}`, `T{}`, `errors.New`, `fmt.Errorf`) get it. Everything else stays `'<inferred>'`.
- **Rust: crates in a workspace, top-level modules in a single crate.** A workspace's crates are its architecture, so each is a module; a single crate's architecture is its top-level modules, so `init` splits it the way it splits a Python package. Test, example, benchmark and fuzz crates (`tests/`, `tests-build/`, `examples/`, `benches/`, `fuzz/`) and directories a workspace excludes are not modules.
- **Rust is resolved per crate, after extraction.** Rust paths need the module tree (`mod` declarations, `#[path]`, `mod.rs` and `x.rs` + `x/` layouts) and the Cargo manifests (`[lib]` names, path and renamed dependencies), which no single file has. The extractor records `use` leaves, `mod` declarations, inline paths and `impl` blocks raw; a crate pass then resolves them to `file:` and `crate:` specifiers, so the project builder needs no Rust knowledge. Cargo.toml is read with a small TOML subset reader (tables, strings, arrays, inline tables), not a dependency.
- **Rust visibility decides what is public.** The public API of a crate is what its root reaches through `pub mod` and `pub use`; a `pub` item in a private module is public only if re-exported. Path resolution follows Rust's visibility too: from outside a crate only `pub` modules are entered, so `axum::serve` is the re-exported function and not the private module of the same name. Items of nested `pub mod`s inside the same archlock module are listed as `child__item`, the same `__` qualification used for name collisions.
- **Inline paths are dependencies.** Rust code can use `crate::util::helper()` or `serde_json::to_string()` without a `use`. Paths in code whose first segment is `crate`, `self`, `super` or a lowercase name not bound by `use` (a crate or a module) are recorded like imports; paths starting with a type (`Vec::new`) are not.
- **`impl` blocks belong to their type.** Inherent methods and associated constants are members of the type wherever the `impl` is; a trait implementation (`impl Display for User`, `#[derive(Clone)]`) is a base, like `implements` in TypeScript. The trait's methods are not repeated, and bases are sorted so moving an `impl` never changes the sketch.
- **Enums carry data and methods.** A Rust enum variant's data is part of its API, so enum members got an optional payload (`Circle: '{ radius: f64 }'`) and enums got methods. `Enum` is written last among the bases (`class Color(str, Enum)`), which is also the order Python requires.
- **Macro bodies are read when they are items.** Libraries like tokio declare most of their API inside `cfg_*! { … }` macros. Item-level macro bodies (and `cfg_if!` branches) are parsed again as Rust with the rest of the file blanked, so positions stay valid; a body that does not parse as items is skipped rather than guessed.
- **Rust spellings in the canonical form:** lifetimes (`'a`, a quote no TypeScript string could close), reference prefixes (`&T`, `&mut T`, distinguished from a TypeScript intersection by position), `+` between bounds, `::` paths, `?Sized` and `macro_rules!`. As with Go, the real-world TypeScript, Python and Go sketches are byte-identical before and after.
- **Java: build modules or top-level packages.** A multi-module build's modules are its architecture, so each source root is a module; inside a single source root, the direct subpackages of the common root package are (`com.acme.shop.order`, `com.acme.shop.billing`), like the subpackages of a Python package. Deeper packages stay with their top-level package, so the number of modules stays readable.
- **Java source roots come from `package` declarations.** `src/main/java/com/acme/Order.java` with `package com.acme` has the root `src/main/java`, whatever the build tool or layout; no `pom.xml` or Gradle script is interpreted. Comments are stripped before reading the declaration, because a `package-info.java` can start with a long Javadoc. A file whose path does not match its package is left out of detection.
- **Java imports are fully qualified names.** A name resolves to the file of its outermost class (`com.acme.Order.Line` → `Order.java`, static imports likewise), a wildcard import to a file of the package. Fully qualified names in code count as dependencies: in types always, in expressions only in the unambiguous form `a.b.Class`, so a variable chain like `order.id.length()` is never mistaken for a package. The JDK (`java.*`, `javax.*`, `jdk.*`, …) is no dependency; other names are external, named by their first two segments.
- **Java visibility is the API.** Public types and their public members; interface members are public unless `private`. `protected` members are not listed, matching TypeScript, although subclasses in other packages can see them. Class modifiers and kinds that change how a type can be used (`abstract`, `final`, `sealed`, records, annotation types) are decorators on the class, which is valid Python and keeps them compared.
- **C#: projects are modules.** A `.csproj` is C#'s unit of compilation and of `ProjectReference`s, so each project is a module, named after the project; a single project is split into its folders. Test, benchmark and sample projects are recognized by their name (`Shop.Tests`, `TestConsole`), their folder or a reference to `Microsoft.NET.Test.Sdk`. Folders of `.cs` files outside every project, which projects pull in with `<Compile Include>`, become modules of their own.
- **Operators are dunder methods.** `operator +` is `@staticmethod def __add__(a: Money, b: Money) -> Money`, with Python's names for the operators Python has (`__eq__`, `__lt__`, `__neg__`, …) and `__implicit__`/`__explicit__` for conversions: the notation stays valid Python and every operator is compared like any other method.
- **C# dependencies come from names, resolved like the compiler does.** A `using` imports a namespace, not a file, and code can use the types of its own and its parent namespaces without one. The extractor records the capitalized names a file uses; a project pass resolves them against the declared types through the file's namespaces and their parents, its `using`s, its project's `global using`s and aliases. A project only sees its own types and those of the projects it references (transitively, as in SDK projects); its own come first. That matters because ASP.NET projects each declare `static class Extensions` in `Microsoft.Extensions.Hosting`: a first match across the repository would link unrelated projects. `using` directives of namespaces in the repository count as dependencies too, except `System.*` and `Microsoft.*`, which projects commonly extend. Extension methods (`services.AddEventBus()`) are found by the called name: a call leads to the file that declares an extension method of that name when its namespace is in scope (the file's namespaces, `using`s and global `using`s) and its project is visible, which also covers the common case of extensions declared in `Microsoft.Extensions.DependencyInjection`. Without types the receiver is unknown, so of several candidates in scope the first visible one counts, the calling project's own first, as for type names.
- **Partial types are merged.** The members and bases of every part go to the part in the first file (in path order), so splitting a class across files never changes the sketch.
- **Nullable suffixes in the canonical form.** A `?` directly after a type that ends it (`string?`, `List<T?>`, `int?[]`) is a suffix, not the start of a conditional type; before `,` `)` `]` `>` or the end that is unambiguous, before `[` the missing space decides. TypeScript's optional tuple elements now read `[T?]` as well; sketches written with the earlier `[T ? ]` still match.
- **One broken sketch does not cascade:** its module still counts as known, and the real parse error is reported first.
- **Typed mode is opt-in.** `"typed": true` lets the TypeScript checker fill in types the code leaves out. It stays deterministic for a given TypeScript version and installed type declarations, but it depends on both, and on other files, so it is a project decision stored in the config (`check` and `accept` must agree) and typed files bypass the per-file cache. Types the checker cannot resolve stay `'<inferred>'` instead of turning into `any`, `import("…")` qualifiers are dropped, and inferred types longer than 200 characters are `'<complex>'`: the full spelling of an inferred Zod schema type is no contract anyone wants to review.
- **A file-hash cache** (in `node_modules/.cache/archlock/` or `.archlock-cache/`) keeps warm runs fast; it is invalidated whenever the archlock build changes.

## `accept` and `diff`

- **`accept`** takes hard content (symbols, signatures, dependencies) from the code and keeps everything a human wrote (paths, entry, strictness, docstrings, comments). It never writes without a confirmation or `--yes`.
- **`diff`** extracts both states from code: the base commit is checked out into a temporary worktree, and both sides are compared as "what `accept` would write". Architecture changes therefore show up even when nobody ran `accept`. The Action posts the result as one comment, found again by an HTML marker and updated on every push.

## `push` and agents

- **The work order** lists, per difference, the target from the sketch, the current code and the difference, plus the module's invariants, the affected sketches and fixed rules (never edit the sketches, stay within `__depends_on__`, run the check until green, never run `accept`). It is written to a file in the cache directory, so no command line gets too long and any agent that reads files can use it. Dependencies the plan declares but nothing uses yet are listed as context, because they say where new code should be connected.
- **Consent and safety:** `push` asks before it starts an agent, warns about uncommitted changes, never commits, re-checks after every round and warns if the agent edited a sketch. Agents get an empty stdin.
- **Claude Code runs with narrow permissions:** it may edit files and run exactly the check command and the configured `agent.verifyCommands`, as `Bash(<cmd>)` plus `Bash(<cmd> *)` (the space keeps a word boundary). Commands containing `* ( ) , ; & | < > ` $` are rejected because they could widen a rule or chain commands. Allowing a test or build command lets the agent run code it wrote; that is the purpose of the option, so it is opt-in and documented.
- **`init --agents`** adds a marked section to `AGENTS.md`/`CLAUDE.md` whose core rule is "propose, do not accept". **`init --with-summaries`** lets the agent add only `# suggested:` lines; any other change to a sketch is rolled back.

## Project infrastructure

- **Releases** use Changesets: merging the "chore: release" pull request publishes to npm with provenance and moves the `v0` tag that the Action is referenced by.
- **The demo GIF** (`demo.tape`, vhs) is a real run with Claude Code; only the agent's silent work is sped up, and the recording says by how much. The CI test of the demo replays recorded changes instead, so it does not depend on an LLM.
- **The landing page** (`site/`) is plain HTML and CSS with 1 KB of JavaScript, system fonts, no cookies and no third-party requests, deployed to GitHub Pages. Its two accent colors mean the two directions: blue for the sketch side and `push`, amber for the code side, `accept` and everything `check` reports. The logo's wordmark is converted to paths from Fira Sans Bold (SIL Open Font License) by `scripts/brand.py`.
- **Key numbers have one source:** `examples/real-world/numbers.json`, written by `regenerate.sh`; `scripts/check-numbers.mjs` fails when README, site, docs or the examples disagree with it.
